## 0. 决策基线（已确认，不再摇摆）

| 决策 | 结论 |

| 产品形态 | **小范围公开**，部署到自有服务器（阶段 4 部署为必选） |

3. 前端保持"哑"——只渲染 API 返回的 JSON。

## 2. 整体架构

```
┌────────────────────────────────────────────────────────┐
│  前端层  web/index.html（静态单页，哑前端）                 │
│          fetch('/v1/recommend') → 渲染卡片                  │
├────────────────────────────────────────────────────────┤
│  服务层  src/api.py（FastAPI · 薄层 adapter）              │
│          /v1/recommend · /v1/health                     │
│          ▸ 不写业务逻辑；删掉它复杂度应全部消失             │
├────────────────────────────────────────────────────────┤
│  算法层  src/recommender.py  ←深模块，小接口               │
│          recommend(query_profile, k) -> list[Recommendation]│
│          ├─ CF 打分 / 过滤 / 配额 / franchise 去重（藏在实现里）│
│          src/evaluate.py（双门槛评估）                    │
├────────────────────────────────────────────────────────┤
│  数据层  src/bangumi_api.py  ←深模块，小接口               │
│          fetch_collections(username) -> list[CollectionEntry]│
│          ├─ 限流/重试/分页/400-兜底 全藏在实现里            │
│          └─ dataset.UserInteractions 接口（真实 seam）     │
│              adapter A: 线上 API · adapter B: 本地 SQLite 缓存│
│          data/：archive dump + collections.db             │
└────────────────────────────────────────────────────────┘
```

**模块要点**（实现时遵循，不解释、直接做）：
- `bangumi_api` / `recommender` 是**深模块**（小接口 + 大量实现藏里面）。
- `UserInteractions` 是**真实 seam**（线上 API + 本地缓存两个 adapter）；引擎构造时注入依赖，不自己 new。
- `api.py` 是**薄层**（删除测试：删掉它复杂度消失）。
- **不建 repository 抽象**（存储只有 SQLite 一个 adapter）。

**技术路线演进**：Popularity Baseline → numpy CF → implicit ALS（扩量）→ 混合（内容特征）→ SASRec（可选）。

## 3. 分阶段会话计划

> 每个阶段标注：**目标 / 你要做什么 / Claude 做什么 / 交付物 / 会话数 / 门禁**。
> 【你】= 人类动作；【Claude】= 生成动作；【协作】= 一起验收。

### 阶段 0：领域模型 + 骨架 + API 客户端（约 1 个会话）

- **目标**：领域语言定死、深模块骨架搭好、真实 API 调通。
- 【你】在 [bgm.tv/dev](https://bgm.tv/dev) 申请 Personal Access Token（需要你的账号，无法代劳）。
- 【Claude】生成 `src/` 骨架、`bangumi_api` 深模块（限流/重试/offset+limit 分页/`limit>total` 400-兜底）、维护 CONTEXT.md。
- **交付物**：能 `fetch_collections("真实用户名")` 返回数据的可运行骨架。
- **门禁**【你】：一次调用成功取回一个真实用户完整"看过"列表，你确认返回内容合理。

### 阶段 1：数据准备（实现 ~1~2 会话 + 爬取墙钟 1~3 小时）

- **目标**：离线条目库 + 1k 种子用户交互落库。
- 【Claude】生成：Archive 导入脚本、种子用户发现管道、`crawl_users.py`（`TARGET_USERS=1000` 参数化、断点续爬、每日配额）。
- 【你】触发爬虫并让它后台跑（或让 Claude 挂后台任务）；等墙钟。
- **交付物**：`collections.db`（subjects + collections）+ 统计报告 + 可复用脚本。
- **门禁**【你】：抽查统计报告（用户数/交互数/缺失率）合理。

### 阶段 1.5：可行性原型（门禁节点 · 约 1 个会话 + 你的判断）

- **目标**：回答唯一重要的问题——*"numpy CF 在稀疏数据上能否打败流行度基线？"*
- 【Claude】生成**抛弃式原型** `scripts/proto_cf.py`（一个命令跑通、纯内存、无测试无抽象），按时间留出 20% 做评估，输出 NDCG@10/Recall@10 对比。
- **门禁**【你·必须亲自判断】：
  - ✅ CF 显著优于流行度基线 → **进入阶段 2**。
  - ❌ 打不过 → 停下来重评（扩种子用户 / 换 ALS / 改相似度），**不带着败仗搭服务层**。

### 阶段 2：MVP（约 2~4 个会话）

- **目标**：输入 username → top-20 推荐 + 模板理由，全链路跑通。
- 【Claude】生成：`recommender` 深模块（阶段 1.5 验证过的算法 + 过滤已收藏/抛弃 + top-N）、`reason` 模板引擎、`UserInteractions` 双 adapter、`api.py` 薄层（`POST /v1/recommend`）、`web/index.html` 轻量单页、`evaluate.py` 固定评估子集。
- **交付物**：可运行全栈 demo + 评估基线报告。
- **门禁（双门槛）**【你】：
  1. 固定评估子集上 NDCG@10/Recall@10 相对流行度基线提升 **≥15~20%**；
  2. 你自己抽查 **10 个熟知用户名**，主观判断"能看"。

### 阶段 3：扩量 + 混合推荐（约 3~5 会话 + 爬取墙钟 1~3 天）

- **目标**：发布数据规模 20k + 显著提升质量 + 解决冷启动。
- 【Claude】生成：内容特征（标签/题材/年份/staff）、混合融合（`score=α·CF+(1−α)·内容`，α 网格搜索）、MMR 多样性重排、冷启动（新用户流行度兜底、新条目内容近邻）、增量刷新（每周 cron）、版本对比报告。
- 【你】启动 1k→20k 扩量爬虫（后台跑 1~3 天墙钟）。
- **阶段 3-1 已做**（2026-08-05）：IDF 加权上线、λ 归零；离线指标 NDCG +8% / Recall +25%（Recall 过门槛线）。**评分中心化在 742 用户下被实测否决**（NDCG −14%），证据与原因见 `docs/adr/0001`。
- **阶段 3-2 已做**（2026-08-05）：双通道（NDCG −11.8%）与极性二值（+4.0%）均不如 IDF 二进制（+8.0%）——**评分信号在 6 种形态下全部不如"只看过"**，维持 idf_binary（λ=0）为产品算法。*注：此结论在 ~1k 规模得出；20k 全量规模下 1-10 线性加权反转（Recall +6.7% / NDCG +5.8%），见阶段 3-9 与 docs/adr/0005。*
- **阶段 3-3 已做**（2026-08-05）：KNN 候选池收敛，K=200 定稿。离线指标升至 **NDCG +8.5% / Recall +36.8%**（Recall 远超门槛线）。实现为 `score_items(..., knn=200)`。
- **阶段 3-4 已做**（2026-08-05）：内容特征混合（meta_tags 与 tags 两种特征源、α 网格）**全部劣于纯 CF**，不上线。内容信号保留给冷启动场景。NDCG 15-20% 的路径改为**扩量 20k** + 可选 ALS。
- **阶段 3-5 已做**（2026-08-05）：ALS（implicit）全部配置劣于近邻冠军（最优 NDCG −15.5%），**不启用**。产品算法定型：`idf_binary + KNN=200, λ=0`。评分/内容/ALS 三类增强均判定为"待扩量后重验"，NDCG 15-20% 的唯一路径是**扩量 20k**。
- **方向转折**（2026-08-06）：20k 全量评估显示 CF 的 NDCG 结构性追不上流行度（最佳 −8.9%），但 Recall +23%。用户拍板转向**发现方向**："不要推荐全是热门"。门槛 1 判据从"NDCG 超流行度"改为 **Recall 保持 + 列表冷门占比**（见 `docs/adr/0002`）。"20k 后重验评分/内容/ALS"的 TODO 随之**作废**——它们的目标（NDCG 追热）已不再是产品目标。
- **阶段 3-7 已做**（2026-08-06）：冷门配额 **20 中 8**（热度排名 > 3000 = 冷门），`quota_rank()`。Recall 零损失，冷门占比 2%→40%（见 `docs/adr/0002`）。
- **阶段 3-8 已做**（2026-08-07）：franchise 去重 + 排除已看续作（关系类型 2/3/6）。平均每条列表 5 条续作冗余被清除，Recall 无损（见 `docs/adr/0003`）。
- **阶段 3-9 已做**（2026-08-08）：**评分加权 User-CF（1-10）+ 口味排除四分以下**。全量 12000 重度用户/700 评估实测：`A[u,i]=idf[i]×rate` 产品路径 Recall +6.7% / NDCG +5.8%（相对原二值）；口味信号排除 rate≤4（低分不再帮推同类）；franchise 排除仍基于全部已看。成本零（稀疏结构不变）。数据源迁移 `collections_rated_rate`（见 `scripts/build_rated_table.py`）。**推翻阶段 3-2 的"评分不帮忙"**——评分信号需数据密度，~1k 规模测不出（见 `docs/adr/0005`）。
- **阶段 3-10 已做**（2026-08-08）：**两区输出（动画推荐 / 冷门发现），替代混合配额**。产品不再把热门与冷门混合进一个列表（阶段 3-7 的"20 中 8"配额被取代）：`recommend()` 返回 `RecommendResult(normal, cold)`，两区共用同一份 CF 分与过滤、仅按热度池子切分（正常区 = 非冷门池 top-20，冷门区 = 冷门池 top-20）；前端顶部 tab 切换、各 20 条、去掉冷/热角标；导出 JPG 跟随当前 tab 分开导出。API 响应结构破坏性变更（`count`/`recommendations` → `normal`/`cold`）。评估脚本同步两区（见 `docs/adr/0006`）。
- **阶段 3-11 已做**（2026-08-08）：**"不感兴趣"功能**。前端每条推荐可点 ✕ 隐藏，隐藏列表存浏览器 **localStorage**（按用户名分 key，**无需账号登录**）；推荐池从 20 扩到 **40**（前端请求 `k:40`），隐藏后空位由池内下一位替补；meta 显示"已隐藏 N 条"，可展开恢复 / 清空；导出 JPG 跟随当前可见（已过滤）列表。引擎/API 零改动（`k` 本就是请求参数，候选充足性已验证）。隐藏只影响展示层、粒度=单部动画（不做整系列、不进 CF 训练）。
- **门槛 2 待做**（2026-08-07，服务已就绪）：无 10 个熟人，方案 = 你本人自测 + 判别力测试。打开 http://127.0.0.1:8000 用自己账号验证：前 12 条热门贴合口味、后 8 条冷门有"居然想看"的、无已看动画续作占位。
- **门禁（双门槛）**【你】：混合版优于 MVP 版 + 冷启动用例不退化。

### 阶段 4：部署（约 1~2 会话 + 真机验证）

- **目标**：小范围公开的 HTTPS 服务稳定可用。
- 【Claude】生成：Dockerfile + Docker Compose、Caddy/Nginx（自动 HTTPS）、按 IP 限流 + 推荐缓存、健康检查/日志/重训失败告警、运维文档、隐私声明页。
- 【你】手动：准备 VPS/域名/DNS、提供隐私声明文案、**真机上线检查**。
- **验收（双门槛）**【你】：陌生 IP 可用；断网/重训故障可恢复；抽查不退化。
- **可选（阶段 3 之后再定）**：SASRec（PyTorch，约 1~2 会话）——时序留出评估，**打不过混合版则不启用**。

## 4. 技术选型

| 层次 | 选型 | 理由 |
|---|---|---|
| HTTP | `httpx` + `tenacity` | 异步并发 + 重试/退避 |
| 存储 | SQLite（唯一 adapter） | 20k 用户 ≈ 2M 行，单文件够；不为不存在的多存储建抽象 |
| CF | numpy 自研 → `implicit`(ALS) | ALS 对隐式反馈稳、可扩展 |
| 深度 | PyTorch（仅阶段 4 可选 SASRec） | 不为了用而用 |
| API | FastAPI | 异步、Pydantic、自动文档 |
| 前端 | 静态 HTML + JS（无框架） | 已是 SPA 模式；日后换 React/Vue 只换前端文件夹 |
| 实验 | `experiments/` JSON | 避免早期引入重量级工具 |
| 部署 | Docker Compose + Caddy | 单机零负担；Caddy 自动 HTTPS |
| 调度 | cron / APScheduler | 每周刷新 + 重训 |

## 5. 数据方案

- **条目元数据**：Archive dump（每周三更新，GitHub 下载），含聚合评分/收藏数/标签。**不耗 API 配额**。
- **用户收藏（唯一途径：API 爬取）**：`GET /v0/users/{username}/collections?subject_type=2&type=2&limit=50&offset=0`。
  - offset+limit 分页，默认 `limit=30`、上限 100；**已知 bug：`limit` 大于总收藏数返回 400** → 先 `limit=1` 拿 `total`，再按 `min(50,total)` 分页（兜底藏在 bangumi_api 深模块）。
- **Archive 不含用户收藏**（`favorite` 只是聚合统计）——这是必须 API 爬取的根本原因。
- **信号分层**：`看过+rate>0`=显式正样本；`看过+rate=0`=隐式正样本；`抛弃`=排除；`想看`=暂不用。
- **离线批量**：Archive 每周同步；用户收藏按需增量（新 username 即时拉取+缓存，已缓存用户每周刷新）。
- **SQLite 表**：`subjects(id, name, name_cn, summary, tags, rating_score, rating_total, collection_total, date, platform)` + `collections(user_hash, subject_id, state, rate, tags, comment, updated_at)`。

## 6. 评估与迭代

- **指标**：NDCG@10、Recall@10、Precision@10、MRR；辅助：覆盖率、题材多样性。
- **强制基线**：Popularity Baseline。打不过它＝白做。
  - **2026-08-06 修订**：20k 下 CF 的 NDCG 结构性追不上流行度（追热=流行度的主场），门槛 1 判据改为 **Recall 保持 + 冷门占比**（产品转"发现"，见 ADR 0002）；Recall 不再低于纯 CF、冷门占比达标即视为过线。
- **固定评估子集**：20~50 个重度用户（收藏≥50），时间留出最近 20%，单轮 <10 分钟。
- **双门槛**（每轮迭代都跑）：
  1. 相对流行度基线提升 ≥15~20%；
  2. **你**抽查 10 个真人用户名。
- **迭代纪律**：每次只改一个变量；config + 指标写入 `experiments/`。迭代本身由 Claude 执行，但**验收判断永远在你**。

## 7. 风险与注意事项

| 类别 | 风险 | 对策 |
|---|---|---|
| 合规 | 过度抓取、违反 API 条款 | 礼貌限流、只读公开数据、条目元数据走 Archive；不二次分发原始数据 |
| 隐私 | username 属个人信息；收藏组合可识别个体 | 存哈希；数据最小化；页面加隐私声明 + 数据删除入口 |
| 滥用 | 陌生人刷接口 | 按 IP 限流 + 推荐结果缓存 |
| 性能 | CF 全量相似度 O(n²) | 倒排索引 + 只算共同收藏用户；热门用户预计算 |
| 安全 | 无 HTTPS 就公开 | Caddy 自动 HTTPS |
| 维护 | Archive 周更、API 变更、模型漂移 | 刷新/重训脚本化 + cron + 告警；API 客户端封一层 |
| 发布 | 封面图版权 | 服务器侧中转 + 落盘缓存（2026-08-07 实测 lain.bgm.tv 大陆直连超时，只发链接大陆用户会裂图）；小范围个人项目，随用随弃 |

## 8. 执行节奏：会话 vs 硬性日历时间

### 压不掉的"硬性日历时间"（该等还是要等）

| 事项 | 日历时间 | 为什么压不掉 |
|---|---|---|
| Archive dump 下载/导入 | ~数小时 | 网络 + 数据量 |
| 1k 爬取 | 1~3 小时墙钟 | API 限流是**物理约束** |
| 1k → 20k 爬取 | 1~3 天墙钟（分几天跑） | API 限流是**物理约束** |
| 每周增量刷新 + 重训 | 每周循环 | 数据时效性 |
| 阶段 1.5 门禁 + 双门槛抽查 | 分钟级评估 + **你的判断** | 决策必须真人做 |

### 会被 vibe coding 大幅压缩的实现时间（= 会话数）

| 阶段 | 会话数 | 说明 |
|---|---|---|
| 阶段 0 骨架 | ~1 | 生成 + 你验证 API 返回 |
| 阶段 1 爬虫/导入 | 1~2 | 脚本快，**大头是爬取墙钟** |
| 阶段 1.5 原型 | ~1 | 门禁：你的判断 |
| 阶段 2 MVP | 2~4 | 引擎 + 理由 + API + 页面 |
