# ADR 0005：评分加权 User-CF（A[u,i]=idf[i]×rate）+ 口味排除四分以下

日期：2026-08-08

## 背景

ADR 0001/阶段 3-2 的结论是"评分信号 6 种形态全部劣于只看过二值"。但那些实验在 ~1k 规模、旧判据（NDCG 追热）下做的。产品后来转向"发现"方向（ADR 0002），判据改为 **Recall 保持 + 冷门占比**。用户提出两个新诉求：

1. **按 1-10 分值加权**——让打分参与计算；
2. **排除四分以下**——用户打低分（≤4）的动画不应再"帮推"同类。

成本问题：User-CF 的计算量由稀疏矩阵**非零元数量**决定、与数值无关。加权只是把 `A[u,i]=idf[i]` 换成 `idf[i]×rate`，稀疏结构完全不变 → **零额外成本**（实测矩阵构建 0s、评估耗时相同）。

## 数据（全量 12000 重度用户 / 700 评估用户，产品路径 CF+franchise+配额）

| 配置 | 矩阵 | 口味信号 | Recall@10 | NDCG@10 | vs 二值 |
|---|---|---|---|---|---|
| binary（原产品） | idf 二值 | 全部 rate>0 | 0.0222 | 0.1039 | — |
| rated | idf×rate | 全部 rate>0 | 0.0235 | 0.1090 | +5.9% / +4.9% |
| **excl_q（产品）** | idf×rate | **rate>4** | 0.0237 | 0.1099 | **+6.7% / +5.8%** |
| excl_both | idf×rate，rate>4 | rate>4 | 0.0237 | 0.1099 | +6.9% / +5.7% |

关键观察：
- **效果随规模翻转**：600 用户矩阵下加权 Recall −6%，3000 用户 −5%，12000 用户 **+6.7%**。评分信号需要足够数据密度才体现信息量——这解释了 ADR 0001 在 ~1k 规模为何失败。
- **excl_q 与 excl_both 产品指标几乎相同**：低分对在矩阵里权重本来就轻（rate 1-4），剔除与否无差别。
- 冷门占比恒定 40%（配额强制），评分加权不影响发现方向。

## 决策

- **产品启用评分加权**：`build_encoding(..., values=rate)`，`A[u,i]=idf[i]×rate`（1-10 线性）。稀疏结构不变、零成本。
- **口味信号排除四分以下**：`recommend()` 里 `taste = [e for e in profile if e.rate > 4]`，`q[i]=idf[i]×rate`。**franchise 排除与 nsfw 判断仍基于全部已看（rate>0）**，避免低分动画的续作重新进入候选。
- 旋钮：`matrix_min_rate`（默认 0）、`taste_min_rate`（默认 4）。
- 数据源迁移：物化 `collections_rated_rate`（rate>0 + rate + 覆盖索引），见 `scripts/build_rated_table.py`。旧 `collections_rated`（无 rate）不再作为产品数据源。

## 后果

- 排序质量与发现覆盖双提升（Recall +6.7% / NDCG +5.8%），成本零。
- **用户打低分的动画不再正向影响其推荐**：不进口味向量，也不占候选（本就在 already），其续作仍被 franchise 排除。打低分与"没看过"的差别被区分开（二值时二者等价，都是正信号）。
- ADR 0001 的"评分不帮忙"结论在 20k 规模下**作废**，但保留其方法学：评价必须在全量规模、按产品判据重跑（见 `scripts/experiment_rating_weight.py`）。
- 服务器启动加载从 ~15s 增至 ~43s（rate 列使扫描变慢），可接受（仅启动一次）。
- 增量刷新数据后需重跑 `build_rated_table` 迁移。
